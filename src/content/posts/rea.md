관련 논문 링크: [Reveree: Diagnosing LLM Reverse-Engineering Agents](https://arxiv.org/pdf/2609.01185v1)



이 논문의 핵심은 “AI가 리버싱 문제의 정답을 맞혔는지만 보는 것이 아니라, 분석 과정에서 무엇을 이해했고 어디서 막혔는지까지 평가해야 한다”는 것이다.

기존의 정답률 중심 평가에는 한계가 있었다. 바이너리의 핵심 동작을 거의 이해했지만 마지막 정답을 구하지 못한 AI와, 처음부터 분석에 진전이 없었던 AI가 모두 동일한 실패로 처리된다. 반대로 공개된 풀이를 학습 과정에서 기억한 AI가 정답을 내면, 실제로 바이너리를 분석해서 해결한 것처럼 평가될 수 있다.

연구진은 이러한 한계를 보완하기 위해 REVEREE라는 평가 체계를 제안했다. REVEREE는 AI가 정답을 구했는지뿐 아니라, 분석 과정에서 어떤 단계에 도달했고 어떤 행동을 반복했는지도 평가한다. 분석 단계는 파일 형식 파악, 프로그램 구조 파악, 제어 흐름 이해, 알고리즘 인식과 명명, 입력 조건 추출, 풀이 프로그램 작성, 정답 검증의 8단계로 나뉜다.

평가에는 도구 실행 기록과 LLM 심사자를 함께 사용했다. 파일 정보를 확인하거나 풀이 스크립트를 작성한 사실은 실제 실행 기록으로 판별하고, 알고리즘이나 입력 조건을 이해했는지는 LLM 심사자가 판단하도록 했다. 이때 심사자에게 정답과 성공 여부를 숨기고, 판단의 근거가 되는 분석 기록을 제시하게 해 결과만 보고 이해도를 추정하는 일을 줄였다.

실험은 picoCTF와 NYU-CTF에서 가져온 리버싱 문제 88개와 모델 9종을 대상으로 진행했다. 에이전트 실행 환경은 D-CIPHER로 고정해 모델에 따른 차이를 비교했다. 이 중 모델 4종에서는 기본 프롬프트, 가설 기록 방식인 Ledger, 추론과 행동을 연결하는 ReAct, 실패를 돌아보는 Reflexion도 비교했다.

실험 결과, 어려운 문제에서 가장 큰 병목은 도구 사용보다 분석 결과의 의미를 이해하는 과정에 있었다. AI는 디컴파일 등을 통해 프로그램 구조를 파악해도, 핵심 알고리즘을 알아내거나 정답 입력이 만족해야 할 조건을 추출하는 단계에서 자주 막혔다. 이는 분석 도구를 사용할 수 있다는 사실과 프로그램의 동작을 이해한다는 것이 별개의 능력임을 보여준다.

시간과 자원을 더 제공하는 효과도 제한적이었다. 연구진이 예산이나 실행 횟수를 늘리고 포기하지 않도록 지시했을 때, 해당 실험에서 기존 실패 중 해결로 바뀐 비율은 약 10~15%였다. 연구진은 이를 단순한 자원 부족만으로 설명하기 어렵고, 이해 능력의 한계가 작용했을 가능성이 있다고 해석했다. 또한 더 크거나 새로운 모델, 더 높은 추론 설정이 항상 좋은 결과로 이어지지는 않았다.

성공과 실패는 행동 패턴에서도 차이를 보였다. 성공한 실행은 분석한 내용을 바탕으로 풀이 스크립트를 작성하고 검증하는 단계로 넘어가는 경향이 있었다. 반면 실패한 실행은 같은 명령을 반복하거나 프로그램 전체를 다시 분석하면서도 실질적인 진전을 만들지 못하는 경우가 많았다.

공개된 풀이를 기억했을 가능성도 확인됐다. Opus 4.7은 바이너리 없이 문제 설명만 제공받았는데도 picoCTF 문제의 7.4%에서 정확한 정답을 재현했다. 다만 문제 이름이나 설명을 바꾼 뒤에도 기존에 풀었던 문제 대부분을 다시 해결했다. 연구진은 이를 바탕으로 AI의 성과에 암기와 실제 분석 능력이 함께 작용한다고 설명했다.

다만 이 결과는 공개 CTF 문제와 단일 에이전트 환경에서 얻은 것이다. 설정별 반복 실험도 수행하지 않았기 때문에, 이를 대형 상용 프로그램이나 모든 AI 리버싱 도구의 성능으로 일반화하기는 어렵다.
